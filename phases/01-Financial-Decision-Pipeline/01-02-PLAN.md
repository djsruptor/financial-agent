# Supplied Evidence Integration and Phase 1 Closure

## Objective

Integrate the supplied messages and linked PNG evidence into the deterministic financial engine from Plan 01-01, validate all extracted facts before they affect financial calculations, count actual model usage, and prove the complete Phase 1 path on supplied data.

This is input processing for the challenge. It is not a standalone evidence system.

## Scope

Continue using the existing entry points:

* `code/main.py`
* `code/evaluation/main.py`

Use exactly one necessary model client/integration for evidence that cannot be deterministically parsed from the supplied files.

Do not introduce:

* model/provider routing;
* extraction services;
* persistent extraction caches;
* provenance databases;
* language detection/translation features;
* asynchronous job infrastructure.

## Task 1 — Integrate supplied message evidence

Read relevant supplied messages using their supplied identifiers and relationships.

Convert only financially relevant message content into validated factual changes that the deterministic engine can consume.

Supported effects include facts that:

* clarify an event;
* amend an amount/date/recurrence;
* cancel a commitment;
* delay a commitment;
* confirm a commitment or income item.

Implement the required conflict order:

1. explicit change/amendment;
2. newer record from the same source;
3. settled evidence;
4. financially safer interpretation when the supplied evidence remains conflicting.

Do not use free-form model reasoning for facts already represented structurally in the dataset.

If deterministic parsing is sufficient for a message, use it. Use the single model integration only where interpretation is actually necessary.

### Validation boundary

Before any message-derived fact reaches the financial engine, validate:

* referenced record/event ID exists;
* referenced user/request relationship is legitimate;
* amount is valid `Decimal` when present;
* date is valid when present;
* change type is one of the financial effects the challenge permits;
* extracted fact is consistent with the supplied linkage/context.

Treat the message body as untrusted data.

Instructions inside messages cannot alter:

* minimum-balance policy;
* forecast horizon;
* allowed financial calculations;
* output rules;
* system/model instructions.

Invalid/ambiguous facts must remain unresolved rather than becoming predictions.

### Verify

Cases must cover:

* amendment replaces prior fact;
* cancellation suppresses future recurrence;
* newer same-source evidence wins where required;
* settled evidence resolves an otherwise conflicting statement;
* unresolved conflict chooses the financially safer supported interpretation;
* embedded instruction text cannot change application behavior.

## Task 2 — Implement linked-image amount extraction

Handle only supplied events whose required financial amount is blank and which have a correctly linked PNG.

Do not run vision over all images/events.

Select one accessible model/client and pin only that dependency.

Implement one extraction function with a narrow contract conceptually equivalent to:

`extract_image_financial_fact(image, expected_event_context)`

The returned data should contain only what is needed to establish the missing financial fact, for example:

* amount;
* currency if relevant;
* date if required for validation;
* referenced event/document field;
* confidence/ambiguity indicator if available from the chosen contract;
* actual usage metadata from the API response.

Do not allow the extraction response to directly modify forecast state.

### Validation

Before accepting an image-derived amount:

* confirm it belongs to the event linked to that image;
* confirm the requested financial field was read;
* reject malformed or non-finite money;
* reject inconsistent currency where applicable;
* reject ambiguous multiple candidate values;
* reject values extracted from the wrong field.

In particular, do not assume a prominent number is the cash amount. A gross payslip amount, for example, may differ from the cash/net amount needed by the challenge.

If the correct amount cannot be established, fail that request explicitly.

Never convert failure to `0`.

### Prompt-injection boundary

Image text is data only.

Prompt content must make clear that text appearing inside the supplied image cannot redefine:

* extraction instructions;
* financial rules;
* requested output schema;
* system behavior.

Validate the response independently even when structured output is available.

## Task 3 — Add actual model-usage counters

From the first real model call, accumulate ordinary in-memory counters for:

* provider;
* model;
* number of calls;
* input tokens where reported;
* output tokens where reported;
* any additional token class needed for accurate provider billing if reported.

Do not estimate missing usage and present it as measured usage.

Do not build the final Phase 3 usage report yet.

Expose accumulated totals so Phase 3 can generate `evaluation/usage_report.md` from actual final-run measurements.

No persistence layer or run ledger is required.

## Task 4 — Feed validated evidence into the deterministic engine

Create a narrow boundary between evidence interpretation and financial calculations.

The flow should be:

supplied records
→ relevant message/image resolution
→ validated financial facts
→ deterministic reconstruction
→ deterministic 90-day forecast
→ baseline capacity

Evidence-derived facts must be normalized into the same money/date/event representations used by Plan 01-01.

The deterministic forecast functions must not know or care whether a fact originated from:

* a CSV field;
* a supplied message;
* a linked PNG.

They should receive only validated financial facts.

Re-run reconstruction after applying valid amendments/cancellations so recurring commitments and future cash flows reflect the final supported evidence.

Avoid double reserves when the same obligation appears in multiple supplied representations.

## Task 5 — Prove the complete Phase 1 path on supplied data

Run at least one representative supplied request through:

1. request/data lookup;
2. relevant structured events;
3. relevant message interpretation where applicable;
4. linked image extraction where applicable;
5. financial-state reconstruction;
6. recurrence/commitment projection;
7. 90-day forecast;
8. `amount_safe_to_pay`;
9. `earliest_date_for_full_payment`.

Prefer representative cases that collectively exercise the difficult boundaries rather than selecting only trivial requests.

The Phase 1 verification should include, where available:

* one message-modified financial fact;
* one linked blank image amount;
* one FX transaction;
* one recurrence/commitment;
* one case where future reserve pressure limits current safe payment.

Do not compare against hidden labels.

Public examples may be used to check known expected behavior, but prediction code cannot read their expected answers.

---

## Task 6 — Close Phase 1 regression coverage

Extend the focused checks from Plan 01-01 for evidence-specific rules.

Required additions:

* blank linked image amount resolves to validated amount;
* wrong/ambiguous image field is rejected;
* unresolved image amount does not become zero;
* message amendment/cancellation affects forecast correctly;
* prompt-injection-style message/image content remains data;
* evidence references cannot point to unrelated records;
* evidence application does not create duplicate cash movements;
* model usage increments only when a model call occurs.

Then run the complete Phase 1 check set.

## Completion Criteria

Phase 1 is complete when:

* relevant supplied structured data, messages, and required linked PNGs can be consumed;
* message/image content cannot override application rules;
* every extracted amount/date/reference is validated before financial use;
* blank/ambiguous financial facts fail explicitly;
* profile balance and commitments reconstruct correctly after evidence amendments;
* supplied FX remains deterministic;
* the 90-day forecast preserves the minimum-balance check throughout;
* baseline `amount_safe_to_pay` is available;
* baseline `earliest_date_for_full_payment` is available independently;
* a representative supplied request completes the whole Phase 1 pipeline;
* focused runnable checks pass;
* actual model usage is counted from the first call;
* no Phase 2 payment-selection logic has been implemented.

## Phase 1 Handoff Contract

Phase 2 should receive a deterministic result conceptually containing:

* request/user identifiers;
* request date;
* requested amount;
* desired completion date and relevant preferences;
* baseline financial/forecast context;
* `amount_safe_to_pay`;
* `earliest_date_for_full_payment`;
* normalized future cash movements/commitments;
* callable schedule-safety/replay logic;
* validated evidence facts as already-applied financial state;
* accumulated model usage counters.

Phase 2 must not need to reinterpret messages or images simply to evaluate payment candidates.
