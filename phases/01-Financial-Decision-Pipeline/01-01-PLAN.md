# Deterministic Financial State and Forecast

## Objective

Implement the deterministic core that takes one supplied request and its relevant structured financial records, reconstructs the user's financial state at the request date, produces the 90-day baseline cash forecast, and calculates:

* `amount_safe_to_pay`
* `earliest_date_for_full_payment`

Do not implement payment-plan selection, spending adjustments, final CSV generation, generalized evidence infrastructure, or provider/model integration in this plan.

The output of this plan must be reusable by Plan 01-02 after supplied message/image facts have been validated.

## Scope

Work primarily in:

* `code/main.py`
* `code/evaluation/main.py`

Add one helper file only if `code/main.py` becomes materially difficult to follow. Do not pre-create a package hierarchy or abstraction layer.

Use:

* standard-library `csv`
* `pathlib`
* dictionaries/lists
* `Decimal`
* `datetime` / `calendar`

Do not use floats for monetary calculations.

## Task 1 — Resolve the financial/date rules that block implementation

Before implementing forecast behavior, inspect the repository's authoritative `problem_statement.md`, original instructions, and supplied public examples specifically for:

* whether the 90-day window is inclusive or exclusive at either boundary;
* ordering of cash movements and affordability checks occurring on the same date;
* exact request-date treatment;
* settlement date versus transaction/request date for cash recognition;
* recurrence generation rules;
* month-end recurrence behavior;
* treatment of recurrence instances already represented by supplied events;
* minimum-balance comparison semantics;
* supplied FX direction and lookup date.

Resolve only the behaviors needed by Phase 1.

Do not introduce configurable policy objects for ambiguities. Encode the behavior supported by the specification/examples directly.

If the specification/examples do not resolve a behavior, choose the financially safer interpretation and make that decision explicit in the implementation summary rather than silently guessing.

### Verify

The implementation must have one consistent rule for each relevant date/order boundary. Focused checks added later in this plan must exercise those rules.

## Task 2 — Build strict input loading and request snapshot assembly

Implement the smallest set of loading/indexing functions required to read the supplied participant data and assemble one request's relevant records.

The request context must include only records that are legitimately available/relevant at that request date.

Required behavior:

1. Parse required IDs, dates, amounts, statuses, currencies, and request attributes.
2. Parse monetary values from strings into `Decimal`.
3. Reject malformed required monetary/date fields rather than coercing them to zero.
4. Keep supplied files immutable.
5. Keep public-example labels/answers completely outside prediction functions.
6. Index records sufficiently to avoid repeatedly scanning the full dataset for every lookup.
7. Join records through supplied identifiers rather than inferred identity.
8. Preserve blank event amounts as unresolved values for Plan 01-02 rather than converting them to zero.

For foreign-currency cash events:

1. use only supplied rates;
2. select the rate according to the specification's settlement-date rule;
3. apply the supplied currency direction exactly;
4. perform the conversion with `Decimal`;
5. fail explicitly when the required supplied rate is unavailable.

No live rates or fallback rates are permitted.

### Verify

Focused runnable checks must include:

* valid local-currency amount parsing;
* invalid amount rejection;
* a supplied-style FX conversion;
* missing FX rate rejection;
* date parsing;
* an unresolved blank amount remaining unresolved rather than becoming zero.

## Task 3 — Reconstruct the baseline financial state

Implement pure/deterministic functions that transform the request snapshot into baseline cash state and forecastable commitments.

Start with the profile balance as the already-current balance.

Do **not** replay settled historical transactions into that balance.

Classify supplied cash events so that the baseline correctly handles:

* settled history already represented in the profile balance;
* pending debits;
* pending credits;
* failed transactions;
* cancelled transactions;
* supported future income;
* confirmed commitments;
* unrealized investments/value;
* real linked cash movements such as refunds or investment-sale proceeds;
* duplicate representations of the same movement.

Required rules:

* reserve pending debits;
* exclude pending credits from available cash;
* exclude failed/cancelled events;
* exclude unrealized investment value;
* count supported income on its actual settlement date;
* do not remove legitimate linked movements merely because values/dates are similar;
* do not count one economic movement twice.

Represent unresolved message/image-dependent facts explicitly so the forecast cannot accidentally use them.

### Recurring flows

Implement recurrence inference only where supplied evidence supports recurrence.

The logic must:

* distinguish recurring versus one-time flows;
* respect known amendments/cancellations once supplied as validated evidence;
* avoid generating duplicate occurrences already represented by actual events;
* cover essential variable spending conservatively;
* protect required categories;
* avoid reserving the same economic obligation twice.

Design this as deterministic input/output logic. Plan 01-02 will supply validated evidence modifications to it; do not embed model calls here.

### Verify

Add cases for:

* profile balance plus settled history does not double-count;
* pending debit lowers future capacity;
* pending credit does not increase capacity;
* failed/cancelled transaction has no cash effect;
* unrealized investment value is excluded;
* a real refund/sale proceeds remains distinct;
* duplicate representations are counted once;
* recurring expense generation does not duplicate an existing occurrence.

## Task 4 — Implement the 90-day baseline forecast

Build a deterministic forecast function that takes:

* request date;
* starting/profile balance;
* preferred minimum balance;
* normalized dated cash movements;
* supported recurring flows;
* requested expense amount.

Produce a chronological 90-day balance path.

The forecast must evaluate minimum-balance safety **throughout the period**, not only at the final date.

Keep enough internal structure to replay arbitrary candidate payment schedules in Phase 2, but do not implement candidate selection yet.

A useful interface should conceptually support:

`check_schedule(forecast_context, payments) -> safe/unsafe + balance path`

without creating a planner framework.

### Baseline capacity

Calculate `amount_safe_to_pay` for a hypothetical payment on `request_date` before any optional spending changes.

Requirements:

* `0 <= amount_safe_to_pay <= requested_amount`
* paying that amount must preserve the preferred minimum balance throughout the verified horizon;
* baseline capacity cannot depend on future Phase 2 spending adjustments.

Do not infer payment-method eligibility here.

### Earliest full-payment date

Independently calculate the earliest date in the forecast on which one full payment of `requested_amount` could occur while preserving the minimum balance throughout the remaining verified forecast.

This calculation:

* ignores payment preferences;
* uses no optional spending changes;
* searches from the request date according to the resolved same-day rule;
* returns blank/`None` when no safe date exists inside the verified horizon.

Do not derive this date from `amount_safe_to_pay`; evaluate it independently.

### Verify

Include checks for:

* zero safe capacity;
* partial safe capacity;
* full amount safe immediately;
* future full-payment date;
* no full-payment date within 90 days;
* a payment that looks affordable initially but later causes a reserve breach;
* exact minimum-balance boundary;
* final-day/date-boundary behavior;
* same-day cash-flow ordering.

## Task 5 — Establish the focused Phase 1 regression checks

Use `code/evaluation/main.py` as the existing place for runnable financial checks.

Keep this deliberately small. Do not introduce pytest or a generic testing framework unless already required by the repository.

The checks from Tasks 2–4 must be runnable together and fail with a non-zero result/assertion when a rule breaks.

At minimum cover:

1. snapshot balance not replayed;
2. duplicate versus legitimate linked movement;
3. invalid money;
4. supplied FX/date handling;
5. pending debit/credit handling;
6. reserve breach during the forecast;
7. recurrence/date-boundary behavior;
8. safe-to-pay bounds;
9. earliest-full-payment independence.

The public sample labels may be used later for evaluation, but they must never enter the prediction path.

## Completion Criteria

Plan 01-01 is complete when:

* one structured request can be loaded into a validated request snapshot;
* foreign currency uses supplied dated rates only;
* financial state is reconstructed without replaying settled history;
* recurring and future commitments can be represented deterministically;
* a 90-day baseline cash path is generated;
* `amount_safe_to_pay` is calculated;
* `earliest_date_for_full_payment` is calculated independently;
* unsafe reserve breaches are detected anywhere in the horizon;
* unresolved evidence never silently becomes zero or a guessed fact;
* focused checks pass;
* no payment-plan selection or output-generation code has been added.
